# РязДетейлинг — бэкенд

Node.js/Express API: онлайн-запись с защитой от двойной записи, авторизация
администратора по паролю (хэш, не открытый текст), уведомления в Telegram о
новых заявках. База данных — SQLite (отдельный сервер БД не нужен).

## Что уже сделано

- Пароли администраторов хранятся в БД в виде bcrypt-хэша, а не в JS на фронтенде
- Вход создаёт сессию на 12 часов в HttpOnly-cookie (токен в `localStorage` не хранится), все админские запросы требуют её
- Заявки хранятся в SQLite, а не в localStorage браузера — видны с любого устройства
- Слот `дата+время` защищён уникальным индексом в БД — двойная запись физически невозможна, даже если два клиента отправят форму одновременно
- При новой заявке отправляется уведомление в Telegram
- Есть защита от спама (rate limit) на формы записи/сообщений и на попытки входа

## Деплой на VPS (пошагово)

1. **Возьмите VPS** с Ubuntu 22.04/24.04 (подойдёт самый дешёвый тариф — 1 vCPU,
   1 ГБ RAM хватит с запасом). Например: Timeweb Cloud, Selectel, Reg.ru.

2. **Установите Node.js** (версия 20+):
   ```bash
   curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
   sudo apt-get install -y nodejs
   ```

3. **Загрузите файлы бэкенда на сервер** (например, через `scp` или `git`):
   ```bash
   scp -r backend/ user@ваш_сервер:/home/user/ryazdetailing-backend
   ```

4. **Установите зависимости**:
   ```bash
   cd ryazdetailing-backend
   npm install --omit=dev
   ```

5. **Настройте `.env`**:
   ```bash
   cp .env.example .env
   nano .env
   ```
   Обязательно замените:
   - `JWT_SECRET` — длинная случайная строка, не короче 32 символов (команда для генерации есть в `.env.example`); короче сервер не запустится
   - `ADMIN_PASSWORD` и `MANAGER_PASSWORD` — реальные надёжные пароли
   - `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — см. раздел ниже
   - `FRONTEND_ORIGIN` — реальный домен сайта (`https://ryazdetailing.ru`)

6. **Запустите сервер через pm2** (чтобы работал в фоне и поднимался после
   перезагрузки/падения):
   ```bash
   sudo npm install -g pm2
   pm2 start server.js --name ryazdetailing-api
   pm2 save
   pm2 startup   # выполнить команду, которую покажет pm2
   ```

7. **Настройте Nginx как обратный прокси** (чтобы API был доступен по
   `https://ryazdetailing.ru/api/...`, а не по отдельному порту):
   ```nginx
   location /api/ {
       proxy_pass http://127.0.0.1:3000/api/;
       proxy_set_header Host $host;
       proxy_set_header X-Real-IP $remote_addr;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   }
   Готовые конфиги и пошаговая инструкция — в папке `deploy/` (DEPLOY.md).
   ```
   HTTPS проще всего получить через `certbot` (Let's Encrypt, бесплатно).

   Фронтенд (`booking.html`, `admin.html`) обращается к API по
   относительному пути `/api/...` (константа `API_BASE` в начале скрипта
   каждого файла) — это работает только если сайт и API открываются с
   одного домена через этот прокси. Если API будет на отдельном
   поддомене — поменяйте `API_BASE` на полный адрес в обоих файлах.

## Настройка Telegram-уведомлений

1. Напишите **@BotFather** в Telegram, команда `/newbot`, следуйте инструкциям —
   получите `TELEGRAM_BOT_TOKEN`.
2. Узнайте `chat_id`:
   - для личных уведомлений — напишите боту любое сообщение, затем откройте
     `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id": ...}`
   - для группового чата — добавьте бота в группу и сделайте то же самое
3. Впишите оба значения в `.env`.

## Первый вход в админку

После первого запуска сервера в базе автоматически создаются два
администратора — с логином/паролем из `.env` (`ADMIN_LOGIN`/`ADMIN_PASSWORD`,
`MANAGER_LOGIN`/`MANAGER_PASSWORD`). Дальше пароль можно сменить через
`POST /api/auth/change-password`.

**Важно:** сидирование происходит только при пустой таблице администраторов.
Добавить ещё одного админа/менеджера, отключить или удалить учётку, сменить
пароль — всё это теперь делается прямо из панели (раздел «Администраторы»,
доступен только роли admin), через `/api/admins`.

менеджера физически не дают выполнить такой запрос, даже если он напрямую
обратится к API в обход интерфейса.

## Что уже подключено на фронтенде

Весь сайт (`booking.html`, `admin.html`, `reviews.html`, `gallery.html`,
общий `script.js` на всех страницах) теперь работает через этот API, а не
через `localStorage`:

- **`booking.html`** — занятость слотов и отправка заявки
- **`reviews.html`** — список отзывов и отправка нового (с модерацией)
- **`gallery.html`** — вся галерея «до/после»
- **`script.js`** — цены и наличие услуг; телефон, email, адрес, часы
  работы и ссылки на соцсети в шапке/подвале всех страниц; переопределённые
  в админке заголовки и тексты (`data-content`); текст политики
  конфиденциальности в модальном окне
- **`admin.html`** — вход, заявки, сообщения, модерация отзывов, услуги,
  работы, контакты, тексты страниц и политика конфиденциальности — всё
  через API

Это чинит последний из найденных в исходном аудите багов: раньше правки
контактов, текстов и политики конфиденциальности в админке видел только
сам администратор в своём браузере — теперь видят все посетители сайта.

## Что осталось на localStorage

Ничего важного. Учётные записи администраторов, чёрный список и журнал
действий хранятся на сервере (SQLite) и доступны через `/api/admins`,
`/api/blacklist`, `/api/logs`. В браузере остаются только мелкие
пользовательские флажки (например, закрытый баннер про cookie).

## Расписание работы (единый источник)

Расписание хранится структурно в `settings.contacts`: `wstart/wend` (Пн–Пт), `weStart/weEnd` (Сб–Вс), `weOff` (Сб–Вс выходной), `slot` (минут). Админка («Контакты» → «Онлайн-запись») меняет только эти поля. Из них выводится всё остальное:

- текст «График работы» строит сервер при сохранении (`utils/hours.js`), поле в админке только для чтения;
- слоты на форме записи считаются под выбранную дату (будни/выходные, выходной день без слотов);
- публичная и ручная запись проверяются на сервере по тем же часам для конкретной даты;
- `openingHoursSpecification` в JSON-LD обновляется из тех же настроек в `script.js`. Статическая разметка в `index.html` и `contacts.html` соответствует значениям по умолчанию (Пн–Пт 09:00–21:00, Сб–Вс 10:00–20:00).

Если в старой базе нет полей выходных, используются 10:00–20:00 (как в опубликованном графике).

## Картинки

Статичные фото на страницах отдаются в AVIF с запасным WebP (`<picture>` с `<source type="image/avif">`; фоны шапок — `image-set()` с запасным объявлением для старых браузеров). У каждого `<img>` указаны `width` и `height`, чтобы страница не «прыгала» при загрузке. AVIF в среднем на ~20% легче WebP. Для новых картинок: положите `.webp` в `assets/`, выполните `python3 deploy/make-avif.py assets/новый.webp` и оберните тег в `<picture>`. Фото, загружаемые через админку (работы, отзывы), остаются в исходном формате.

## Безопасность страниц: CSP без `unsafe-inline`

Страницы сайта (HTML) на VPS раздаёт Nginx, поэтому защитные заголовки, включая `Content-Security-Policy`, задаются в `deploy/nginx-security-headers.conf` (подключается в `nginx-ryazdetailing.conf`). Node выставляет ту же политику на `/api` и `/uploads` (`server.js`).

Политика: `script-src 'self'; style-src 'self'; style-src-attr 'unsafe-inline'; …`. Это значит:

- внедрённый `<script>` или `onclick="…"` браузер **не выполнит**; на сайте нет inline-JS, `<style>`-блоков и атрибутов `onclick/onchange/oninput`;
- атрибуты `style="…"` по-прежнему разрешены (их много в разметке и в карточках, которые строит JS), но выполнять код они не могут;
- внешних ресурсов нет (шрифты, картинки, скрипты — свои); разрешён только iframe Яндекс.Карт.

**Правила для разработчика**
- Не пишите `onclick="…"` и не вставляйте `<script>`/`<style>` в HTML. Стили — в `css/*.css`, скрипты — в `js/*.js` и `admin-app/*.js`.
- Обработчик события — через `data-click`, `data-change` или `data-input` (см. комментарий в `js/actions.js`): `<button data-click='[["go","bookings",{"$":"this"}]]'>`. Функцию нужно зарегистрировать: `RDActions.register({ имя: window.имя })`.
- В разметке, которую строит JS, используйте `RDActions.attr('click', [["имя", аргумент, …]])` — аргументы передаются как данные и экранируются.
- Новый внешний ресурс (картинка, шрифт, виджет) потребует правки политики в `nginx-security-headers.conf` **и** `server.js`.

Старые браузеры, не знающие `style-src-attr` (Safari до 15.4, Firefox до 105), применят общий `style-src` и могут не показать inline-стили. Для 2026 года это редкость.

## Структура админки (frontend)

`admin.html` содержит только разметку. Стили вынесены в `admin-app/admin.css`, логика разделена на файлы в `admin-app/`:

| Файл | За что отвечает |
|---|---|
| `core.js` | хранилище, API-клиент (`apiFetch`), вход, навигация, общие хелперы |
| `dashboard.js` | дашборд |
| `bookings.js` | заявки и расписание |
| `messages.js`, `reviews.js` | сообщения, отзывы |
| `catalog.js` | услуги и работы |
| `finance.js` | финансы |
| `access.js` | администраторы и чёрный список |
| `system.js` | журнал действий, настройки, резервные копии |
| `ui.js` | звук и уведомления, модальные окна, экспорт CSV, опрос сервера |
| `site.js` | редакторы контактов, контента и политики конфиденциальности |
| `boot.js` | запуск админки (подключается последним) |

Список заявок на телефоне (≤700px) показывается карточками: ячейки таблицы подписаны `data-label`, а CSS (`.tcards` в `admin.css`) перестраивает строки в блоки; на планшете и компьютере остаётся обычная таблица. Чтобы так же показать другую таблицу, добавьте ей класс `tcards` и `data-label` в ячейки.

На телефоне (≤700px) боковое меню админки — выезжающая панель: кнопка «Меню» в шапке, затемнение фона, закрытие по Esc, по тапу на фон и после выбора раздела (`toggleSidebar`/`closeSidebar` в `ui.js`).

Это обычные (не модульные) скрипты: переменные и функции общие, поэтому **порядок подключения в `admin.html` важен** — `boot.js` всегда последний. При изменении файла увеличьте `?v=` в ссылках на скрипты в `admin.html`, если не используете `no-cache` в Nginx.

## Матрица прав (RBAC)

Роли: **admin** и **manager**. Права проверяются на сервере (`requireAuth` / `requireRole('admin')`); кнопки в админке скрываются только для удобства.

| Область | manager | admin |
|---|---|---|
| Заявки: просмотр, смена статуса/оплаты, правка, ручная запись | да | да |
| Заявки: ручная запись на прошлую дату / вне рабочего дня | нет | да (с пометкой в журнале) |
| Заявки: цена, отличная от прайса | нет | да |
| Заявки: «удалить» (мягкое, статус `deleted`) | нет (ставит статус «Отменена») | да |
| Сообщения: просмотр, отметка «прочитано» | да | да |
| Сообщения: удаление | нет | да |
| Отзывы: просмотр, модерация, ручное добавление | да | да |
| Отзывы: удаление | нет | да |
| Работы (портфолио): просмотр, добавление, правка | да | да |
| Работы: удаление | нет | да |
| Услуги и цены: просмотр | да | да |
| Услуги и цены: добавление, правка, удаление | нет | да |
| Чёрный список: просмотр | да | да |
| Чёрный список: добавление, удаление | нет | да |
| Настройки сайта (контакты, график, контент, политика) | нет | да |
| Администраторы: список, создание, смена роли, удаление | нет | да |
| Журнал действий: просмотр, очистка | нет | да |
| Смена своего пароля | да | да |

Менеджер ведёт операционную работу (заявки, статусы, сообщения, отзывы, портфолио), но не удаляет заявки и сообщения клиентов: «убрать» заявку он может, поставив статус «Отменена». Всё, что меняет деньги, каталог, доступы, настройки и удаление данных, — только admin. Ограничения действуют на сервере (`routes/bookings.js`, `routes/messages.js`); кнопки «Удалить» менеджеру в интерфейсе скрыты классом `admin-only`.

## Страницы услуг для поисковиков (`/services/<slug>/`)

У базовых услуг есть свои `service-*.html`. Услуги, добавленные через админку, раньше открывались только на `service-page.html?id=…` — это страница-шаблон, закрытая `noindex` (одна и та же страница с разным `id` — дубли для поисковика). Теперь для каждой такой **активной** услуги сервер генерирует отдельный статичный файл `services/<slug>/index.html` с уникальными `title`, `description`, `canonical`, OpenGraph и разметкой Schema.org (`Service`, `BreadcrumbList`), а также обновляет `sitemap.xml` и `robots.txt`.

- **Включение:** в `.env` задайте `SITE_DIR` (папка со статикой сайта, где лежит `index.html`) и `SITE_URL` (`https://ryazdetailing.ru`). Без `SITE_DIR` генерация выключена, а карточки продолжают вести на `service-page.html?id=…`.
- **Когда пересобирается:** при старте сервера и через ~2 секунды после любого создания, правки или удаления услуги в админке. Вручную: `npm run build:seo`.
- **Адрес (`slug`)** создаётся один раз из названия и **не меняется** при переименовании: ссылки, уже попавшие в поиск, остаются рабочими.
- **Что не трогается:** базовые услуги со своими `service-*.html` (определяются по JSON-LD в этих файлах) и любые чужие файлы в `services/` — удаляются только страницы, созданные самим генератором (список в `services/.generated.json`).
- Процесс Node должен иметь право записи в `SITE_DIR`. На VPS, где сайт раздаёт Nginx, это та же машина; если сайт лежит на отдельном статическом хостинге, запускайте `npm run build:seo` при деплое.
- `service-page.html` остаётся запасным вариантом (`noindex`, в `robots.txt` закрыта).

## Миграции базы

Новые изменения схемы — только файлами в `migrations/` (`NNN_имя.sql` или `NNN_имя.js` с `exports.up(db)`). Они применяются при старте один раз, по порядку, каждая в транзакции; список применённых — в таблице `schema_migrations`. Первичные таблицы по-прежнему создаются в `db.js` (так не пострадали уже работающие базы). Сейчас: `001_baseline`, `002_service_slug` (slug услуг), `003_indexes` (индексы под записи, отзывы, сообщения, журнал, вход).

## Проверка состояния (health)

- `GET /health` и `/api/health` — процесс жив.
- `GET /health/ready` и `/api/health/ready` — готов принимать трафик: отвечает БД, на диске не меньше `HEALTH_MIN_FREE_MB` (по умолчанию 200 МБ), папка `uploads` доступна для записи. При проблеме — код 503. Наружу отдаются только `ok`/`fail` по каждой проверке, без путей и размеров.

## Тесты

- `npm test` — модульные тесты валидаторов, проверки путей к файлам и slug (встроенный раннер Node).
- `tests/integration.js`, `tests/security.js`, `tests/images.js` — сквозные проверки API (валидация, деньги, фото и WebP, журнал, блокировка входа) на временной копии (инструкция в начале файлов). Пишут в базу — не запускайте на рабочей. `security.js` в конце блокирует вход с вашего IP.

## Правила записи: публичная и ручная

**Публичная форма** (`POST /api/bookings`): включена онлайн-запись, время только в рабочие часы и по сетке слотов, не в прошлом, номер не в чёрном списке, услуга существует и активна.

**Ручная запись** (`POST /api/bookings/manual`, режим оператора) — отдельные явные правила:

| Правило | manager | admin |
|---|---|---|
| Реальная дата/время, корректный телефон, допустимые статусы | да | да |
| Номер в чёрном списке | отказ | отказ |
| Услуга должна быть в справочнике (или не указана) | да | да |
| Цена, отличная от прайса | отказ | можно |
| Прошедшая дата | отказ | можно (запись задним числом) |
| Время вне рабочего дня | отказ | можно |
| Сетка слотов | не требуется | не требуется |
| Занятое время | отказ (уникальный индекс в БД) | отказ |

Любое исключение (прошедшая дата, вне рабочих часов) попадает в журнал действий с пометкой `[исключение: ...]`.

**Правка и перенос существующей заявки** (`PATCH /api/bookings/:id`) — те же границы, что и у ручной записи:

| Что меняют | Правило |
|---|---|
| Дата/время | не на прошедшую дату (никому); не на занятое время (409); менеджер — только в рабочие часы и не на выходной, администратор может и вне графика (с пометкой в журнале); сетка слотов не нужна |
| Телефон | корректный формат; номер из чёрного списка — отказ. Сравнение по цифрам: другая маска не считается сменой номера |
| Услуга | если меняют — только из справочника; неизменённую (даже переименованную позже) не проверяем |
| Цена | менеджеру нельзя менять цену заявки |

Перенос пишется в журнал как `Перенесена запись: было → стало` (+ `[исключение: …]`). Заявку, поставленную администратором вне графика, менеджер по-прежнему может править в остальных полях, если не трогает дату и время.

В форме заявки список времени строится по тому же графику: по выбранной дате (будни, выходные, шаг слота; выходной — «записи нет»), а исходное время редактируемой заявки остаётся в списке с пометкой «вне графика».

## Раздел «Настройки» в админке

Раньше здесь были переключатели и поля, которые ничего не сохраняли (токен Telegram, «авто-бэкап», кнопки «Создать/Восстановить копию» писали только в `localStorage` браузера). Теперь остались только рабочие вещи:

- **Звук уведомлений** — локальная настройка браузера.
- **Telegram** — показывается, настроены ли `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` на сервере (сами значения в админку не отдаются).
- **Контакты и график** — ссылка на раздел «Контакты сайта», где всё реально сохраняется.
- **Резервные копии** — реальное состояние с сервера: время и размер последней копии базы, результат последней выгрузки вне сервера, предупреждение, если копия старше 36 часов или выгрузка не удалась.

Данные берёт `GET /api/system/status` (только admin, `routes/system.js`): читает папку `backups/` и `offsite_status.txt`, которые пишет `deploy/backup.sh`.

## Сетка расписания в админке

Строки сетки берутся из графика в настройках (`ebHoursFor` в `bookings.js`): от самого раннего открытия до самого позднего закрытия за неделю с шагом слота. Ячейки вне рабочих часов дня (например, 09:00 в субботу) и выходные дни затенены и недоступны для новой записи. Заявка, стоящая вне графика (её мог поставить администратор), показывается отдельной строкой «вне графика» и не пропадает. Клик по свободной ячейке открывает форму новой заявки с этими датой и временем.

## Разметка отзывов для поисковиков

На `reviews.html` блок `AutomotiveBusiness` (schema.org) дополняется `aggregateRating` и `review` **только из реальных опубликованных отзывов**: `rdReviewsLD()` в `script.js` вызывается после загрузки списка. Средняя оценка и число считаются по всем опубликованным, в `review` попадают до 10 последних (текст не длиннее 500 символов). Скрытые и ожидающие модерации отзывы не попадают; если опубликованных отзывов нет, рейтинга в разметке нет вообще. Отзывы размечаются только на странице, где они видны посетителю (на главной их нет, поэтому там разметки отзывов нет).

Ограничения: разметка достраивается скриптом в браузере (Яндекс и Google её обрабатывают, но не все боты исполняют JS). Google, как правило, не показывает звёзды для отзывов о собственной организации на её сайте, поэтому на рейтинг в выдаче Google рассчитывать не стоит; для Яндекса и для понимания страницы поисковиком разметка полезна.

## Бэкапы

`deploy/backup.sh` ежедневно делает копию SQLite и `uploads/` в `backups/` (хранится 14 копий). Если задан `OFFSITE_REMOTE` (см. `deploy/backup.env.example`), копии шифруются (gpg) и выгружаются в удалённое хранилище через rclone, проверяются после загрузки, старше `OFFSITE_KEEP_DAYS` дней удаляются. Без пароля шифрования наружу ничего не уходит. Результат последней выгрузки — `backups/offsite_status.txt`, опционально пинг в healthchecks (`HEALTHCHECK_URL`). Проверка восстановления — `deploy/restore-test.sh [--remote]`. Подробности — в `deploy/DEPLOY.md`.

## Вход в админку и безопасность сессии

Сессия администратора хранится в HttpOnly-cookie `rd_session` (SameSite=Strict, путь `/api`,
флаг Secure включается сам при HTTPS). Токен не отдаётся в ответе API и не лежит в `localStorage`,
поэтому скрипт страницы его не видит. Изменяющие запросы по cookie должны нести заголовок
`X-Requested-With: rd-admin` (CSRF-защита) — админка добавляет его сама.

Важно: сайт и API должны открываться с ОДНОГО домена (Render или Nginx, проксирующий `/api`).
Если вынести API на другой домен, cookie с SameSite=Strict работать не будет.

### Блокировка подбора пароля

Поверх лимита «10 попыток за 15 минут» работает прогрессивная блокировка (`utils/loginGuard.js`, счётчики лежат в БД и переживают перезапуск):

| Счётчик | Бесплатных ошибок подряд | Блокировка | Потолок |
|---|---|---|---|
| по IP | 5 | 1 мин, каждая следующая ошибка удваивает срок | 30 мин |
| по аккаунту | 10 | 1 мин, удвоение | 15 мин |

Во время блокировки сервер отвечает `429` с заголовком `Retry-After`, даже если пароль верный. Потолок для аккаунта ниже намеренно: чужак не сможет надолго «запереть» владельца снаружи. Успешный вход сбрасывает счётчики, час без ошибок — тоже. Уже выданная сессия во время блокировки продолжает работать. Для несуществующего логина bcrypt считается так же, как для настоящего, чтобы по времени ответа нельзя было угадывать логины.

### Журнал действий: «было → стало»

Таблица `logs` хранит не только текст, но и JSON `changes` вида `{ "price": ["1200", "1500"] }` — только изменившиеся поля. Покрыты: услуги (цены, названия, фото, активность), работы, отзывы, записи (статус, дата, время, суммы, оплата), настройки сайта; при удалении сохраняется снимок удалённого. Хэши паролей, токены и подобные поля в журнал не попадают. События безопасности (`Неудачный вход`, `Блокировка входа`) пишутся с IP; в журнал попадают первые три ошибки и момент блокировки, чтобы перебор не забивал журнал. В админке изменения видны в колонке «Детали». Просмотр журнала — только роль admin.

## Загружаемые фото: WebP

Фото услуг, работ и отзывов приходят как `data:`-URI и сохраняются файлами в `uploads/…` (в базе только путь). При сохранении сервер (библиотека `sharp`):
- перекодирует в **WebP** (качество 80) и уменьшает до 1600 px по длинной стороне — обычно в 2–5 раз легче оригинала;
- **стирает EXIF**, в том числе GPS-координаты места съёмки (поворот по EXIF при этом применяется);
- отклоняет файлы, которые не декодируются как картинка, и «бомбы» из пикселей (больше 30 Мп); SVG не принимается;
- сохраняет прозрачность PNG.

Если `sharp` по какой-то причине не загрузился, фото сохраняются как есть (загрузка не ломается, в логе предупреждение).

**Уже загруженные фото** можно сжать одной командой — сначала посмотрите, что изменится (ничего не трогает): `npm run optimize:uploads -- --dry-run`, затем сам запуск `npm run optimize:uploads`. Скрипт обновляет ссылки в базе и только после этого удаляет старые файлы; повторный запуск безопасен. **Перед запуском сделайте бэкап** (`deploy/backup.sh`).

## Отслеживание ошибок

Необработанные исключения пишутся в журнал процесса (`pm2 logs`) с пометкой `[fatal]`, после чего процесс перезапускается pm2. Чтобы получать уведомления об ошибках 5xx, задайте `SENTRY_DSN` в `.env` (sentry.io или свой GlitchTip). Имена, телефоны, госномера, cookie, IP и тела запросов в отчёты **не попадают** (вырезаются в `utils/monitoring.js`, есть тест). Но сам сервис Sentry облачный и расположен за пределами РФ — если это важно для вашей политики обработки персональных данных, используйте самохостный GlitchTip или оставьте `SENTRY_DSN` пустым.

## Дополнительные услуги в онлайн-записи

Клиент может отметить на странице записи «Дополнительные услуги» (туда же попадают услуги, добавленные в админке). Раньше эти отметки не отправлялись вообще. Теперь форма шлёт список `extras`, а сервер принимает **только реально существующие активные услуги** (по точному названию, без повторов, без основной, не больше 10; любой мусор в списке игнорируется и не мешает записи) и записывает их первой строкой комментария заявки: `Доп. услуги: …`. Так они видны в админке и в уведомлении Telegram. **Цена заявки — цена основной услуги**: доп. услуги в сумму не включаются, при необходимости её корректирует администратор.

Ссылка «Записаться» со страницы услуги (`/booking.html?service=Название`) теперь предвыбирает услугу, даже если в вёрстке формы она «дополнительная».

Папка `e2e/` рядом с `backend/`: сценарии Playwright (запись клиента → админка; вход → правка записи → выход; права; блокировка входа) и проверки страниц в jsdom. Подробная инструкция — `e2e/README.md`.


## Проверки при старте и тесты

**Сервер не запустится, если:**
- при первом создании пользователей `ADMIN_PASSWORD`/`MANAGER_PASSWORD` короче 12 символов или содержат шаблонные слова («замените», «password», «admin», «qwerty» и т.п.);
- `NODE_ENV=production`, а `SITE_DIR` не задан, в нём нет `index.html`, нет права записи или `SITE_URL` не начинается с `https://`.
  Если SEO-страницы сознательно не нужны (например, демо на Render), задайте `SEO_DISABLED=1`.

**Тесты:**
- `npm test` — unit-тесты (валидаторы, мониторинг, стартовые проверки);
- `npm run test:integration` — integration/security/images/RBAC и гонка за слот; каждый набор идёт на чистой временной копии, рабочая БД не затрагивается;
- `npm run test:all` — всё сразу.
